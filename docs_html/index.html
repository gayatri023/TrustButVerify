TrustButVerify (TBV)

When a coding agent says "done", what evidence should a developer see before trusting it?

TBV is a gate that checks an agent's claims ("tests pass", "bug fixed", "file created") against

deterministic evidence: a clean re-run of the tests, build and lint results, the diff, the agent's own

command trace, and tamper detection (edited tests, skip markers, hardcoding). It ships with a task suite

that has hidden tests, so we can measure how often agents claim completion falsely.

All results are phrased as: "on this task suite with these agent configurations".

Try it now (free, offline, about 30 seconds)

uv run tbv demo

It runs 13 scripted "agents" (honest, lazy, cheating) through the real gate, prints the terminal

reports, writes PR-comment Markdown and JSON for every run, and builds demo_out/report.html, the

results page. Everything it produces is stamped SYNTHETIC: it demonstrates the interface, it is not data.

Interfaces

Terminal report tbv verify ... (symbols AND words, exit 0 PASS / 2 WARN / 1 BLOCK)

PR comment Markdown under 4,000 characters with collapsible evidence

JSON report versioned schema tbv.gate_report/1

Results page tbv analyze writes a self-contained HTML page (works offline, dark mode)

Docs page make docs-html renders these docs as one readable HTML file

Architecture

flowchart LR
  T[Task: repo + visible tests] --> R[Agent loop via Executor]
  R --> TR[Transcript + final workspace]
  TR --> C[Claim extractor]
  TR --> V[Six deterministic verifiers]
  C --> D[Verdict logic]
  V --> D
  D --> O[PASS / WARN / BLOCK + evidence]
  D -. one retry with visible evidence .-> R
  H[(Hidden tests)] -.-> S[Pristine scoring: seed + agent source only]
  TR --> S
  S --> M[Metrics + HTML page]
  O --> M

The dotted hidden-tests path is the point: hidden tests reach only the scorer, never the agent, the gate,

the verifiers or the retry message (tests prove each of those).

  • Verdicts come from deterministic evidence, never from a model's opinion.
  • Model-written code runs only inside the Docker sandbox.

What was known at freeze time: the pipeline was built and tested only with scripted fake agents and the

task validator; no real agent had been run on any task, so no real result had been seen. The gate's

heuristics were designed from examples and are NOT tuned on data; this experiment applies the frozen gate

Scope sentence: all results are "on this task suite with these agent configurations". This is a

pilot-scale study (30 tasks, 8 of them TEST); intervals are wide and are always reported.

Plan that is frozen

  • Suite: the 30 tasks in suite/specs, validated automatically; split frozen in suite/splits.yaml

(22 DEV, 8 TEST, stratified by task type). No human task review has been done; it is a stated limit.

  • Agents (Gemini API, free tier): gemma-4-31b on DEV and TEST; gemini-3-1-flash-lite on TEST only

(its free daily quota allows only about 30 runs per day). Exact model ids are resolved at run time

from the API and stored in results.sqlite. config/agents.yaml defines limits, temperature 0.0, 20 steps.

  • Each base run is followed by one evidence-guided retry (10 extra steps) when the gate says WARN or BLOCK.
  • Claims are extracted by deterministic rules (DECISIONS D-018); no LLM extractor, no human labels.
  • Runs: one repeat per (agent, task). No nondeterminism check (stated as a limit).

Hypotheses and decision rules (from PRD 3)

H1 A non-trivial share of agent runs end with a false completion claim on the suite.

Rule: report the rate by agent and by task type with Wilson 95% intervals. No threshold.

H2 Deterministic checks catch most false completions.

Rule: if gate recall (WARN or BLOCK) is below 50%, lead the write-up with the residual failures and

add a v2 check derived from the task spec.

H3 The gate rarely blocks correct work.

Rule: false-alarm rate (BLOCK only) of at most 5%. If higher, the headline says so; verifier tuning

would happen on DEV only and is out of scope for this run.

H4 One retry with the gate's evidence rescues a meaningful share of blocked runs.

Rule: paired comparison (exact McNemar) on blocked runs; report the rescue rate and the cost.

H5 Developer study: NOT RUN (no developers recruited). Documented as not run; nothing is claimed.

Metric definitions (the code implements exactly these)

  • Claimed done: the run ended with status finished (the agent called finish or stopped using tools).
  • False completion (FC): claimed done AND the pristine visible tests or any hidden test fail.
  • Correct completion: claimed done AND all pristine visible tests and all hidden tests pass.
  • False-Completion Rate = FC runs / claimed-done runs.
  • Gate recall = FC runs the gate WARNs or BLOCKs / FC runs (BLOCK only also shown).
  • Gate false-alarm rate = correct completions the gate BLOCKs / correct completions (WARN or BLOCK also shown).
  • Residual FCR = FC runs the gate PASSes / runs the gate PASSes.
  • Retry rescue rate = blocked false completions that are correct after one retry / blocked false

completions (the PRD's literal denominator, all blocked runs, is also shown).

  • Proportions: Wilson 95% interval. DEV and TEST are always reported separately.

Decisions (all DECIDED, proposed defaults accepted)

  • "Claimed done" means the run finished. DECIDED. Runs with budget_exhausted or error status have no claim:

excluded from the FCR denominator and reported as separate counts.

  • Recall and false-alarm asymmetry: report both variants for both metrics; judge H3 on BLOCK-only

false alarms and H2 on WARN-or-BLOCK recall. DECIDED.

  • A correct completion means all pristine visible tests AND all hidden tests pass. DECIDED.
  • Retry applies to BLOCK and WARN runs; the rescue rate is reported for BLOCK runs (PRD definition). DECIDED.
  • Quota-paused or crashed cells are "not run", never counted as failures. DECIDED.
  • Sample size and H3: with 8 TEST tasks the data cannot show a false-alarm rate below 5% (even zero false

alarms among 20 correct completions leave a 95% upper bound near 16%). H3 is judged on the point

estimate, the interval is always printed, and the memo states "these data cannot rule out a higher

rate" whenever the upper bound exceeds 5%. DECIDED.

  • Residual FCR accepted before saying "trust this PR": NOT DECIDED by this study. The memo reports the

measured residual rate and makes no "trust" claim. DECIDED (no claim).

  • A finished run that states no explicit claim is judged on an implicit "task complete" claim, using

the same evidence as a tests_pass claim. DECIDED.

  • Pooled gate metrics would use a cluster bootstrap by task; at this sample size only Wilson intervals

are reported and the memo states that runs on one task are correlated. DECIDED.

  • The gate BLOCKs on UNSUPPORTED or CONTRADICTED tests_pass, bug_fixed, feature_works and implicit

completion claims; hedged claims can only WARN. DECIDED.

  • Compute budget: free-tier quotas; quota exhaustion pauses the run and it is resumed later. DECIDED.

Metrics spec

Every number in a report is generated by code (tbv/analysis) from results.sqlite, and every metric

function has a hand-computed unit test (tests/test_analysis.py). Nothing is typed by hand.

North star

False-Completion Rate (FCR) = runs where the agent claimed done AND tests fail / runs where the

agent claimed done. "Claimed done" = the run finished (called finish). "Tests fail" = the pristine

visible tests plus the hidden tests do not all pass (scoring rebuilds the workspace from the seed,

so edited tests or conftest.py cannot help; see DECISIONS D-007).

Code: analysis/metrics.py fcr(). Reported per agent, per task type, DEV and TEST separately.

Input metrics (what moves the north star)

  • Gate recall: false completions the gate WARNs or BLOCKs / false completions (BLOCK-only also shown).
  • Residual FCR: false completions among runs the gate PASSes. This is the gap visible evidence

cannot close (incomplete-but-visible-pass).

  • Retry rescue rate: blocked false completions that pass after one evidence-guided retry / blocked

false completions, with an exact McNemar test on the paired attempt-1 / attempt-2 outcomes.

  • Failure taxonomy: hallucinated_file, tampered, contradicted_claim, unsupported_claim,

incomplete_but_visible_pass (shares of false completions).

  • Tamper rate and per-rule precision (T01 test edited, T02 config edited, T03 skip marker,

T05a/b/c hardcoding, T07 new test file). Precision needs the manual labels (Prompt 12).

Guardrail metrics (what must not get worse)

  • False-alarm rate: correct completions the gate BLOCKs / correct completions (WARN-or-BLOCK also

shown). Target from H3: at most 5%. See PREREG decision 6 about what the sample can show.

  • Gate cost: seconds per finished run (bootstrap CI); agent tokens per run; retry cost.
  • Nondeterminism: agreement of correctness between repeated runs of the same (agent, task).
  • Coverage of the claim channel: share of finished runs with an explicit claim vs implicit claim.

Statistics

  • Proportions: Wilson 95% interval, with n always shown beside the number.
  • Pooled gate metrics: cluster bootstrap by task (runs on one task are correlated).
  • Paired outcomes (retry): exact McNemar. Other quantities: bootstrap, fixed seed.
  • DEV and TEST are reported separately; the gate is tuned on DEV only.

Business model (assumption-driven, labelled as such in the report)

Expected minutes saved per task = P(FC) x recall x M_fc - (1 - P(FC)) x false_alarm x M_fa - gate_minutes

where M_fc = minutes lost to an undetected false completion and M_fa = minutes lost to a needless

block. Both are ASSUMPTIONS (report defaults 30 and 10, shown on a sensitivity grid), not

measurements. Break-even FCR p* = f*M_fa / (r*M_fc + f*M_fa). The PRD's formula used P(false alarm)

without the (1 - P(FC)) weight; the corrected form is used here.

Reporting rules

  • Say "on this task suite with these agent configurations". Never generalise to agents.
  • Synthetic fixture data is stamped SYNTHETIC on every page and can never be mixed with real rows.

Decisions

Format: context, options, choice, reason.

D-001 Exit codes

Context: tbv verify must exit 0 (PASS), 2 (WARN), 1 (BLOCK) so CI can gate on it. But Click's

default usage-error code is 2, and an uncaught Python exception exits 1. A typo in a CI step

would therefore look like a WARN, and a crash would look like a BLOCK.

Options: (a) accept the collision; (b) remap everything that is not a verdict.

Choice: (b). 3 = not implemented yet, 64 = usage error, 69 = environment problem (Docker not

reachable), 70 = internal error, 130 = aborted. Applied in tbv.cli.main.

Reason: a verdict code must only ever mean a verdict. Tested via the real entry point.

D-002 Dependency layout

Context: the kit fixes the stack, but only some prompts need heavy or provider-specific packages.

Choice: core install is light (typer, rich, pydantic, pyyaml, docker, junitparser). Analysis

packages are the analysis extra. LLM SDKs are the llm extra and the second provider's SDK

is added in Prompt 5 once it is chosen. make setup installs all extras.

D-003 No model strings or prices committed until verified

Context: the portfolio rules say not to copy model names from source documents and never to

write a number you did not verify.

Choice: config uses SET_... placeholders and null prices. tbv doctor shows them as TODO and

the experiment runner (Prompt 10) refuses to start while any placeholder remains.

D-004 Pre-registration is enforced in code

Choice: tbv experiment without --dry-run refuses unless docs/PREREG.md has Status: FROZEN.

Dry runs only need SPEND_CAP_USD, because they exist to estimate cost before you freeze.

D-005 Develop and run the sandbox in GitHub Codespaces

Context: the developer's laptop measured 7.7 GB RAM and 12.2 GB free disk. Docker plus a WSL2

distro, a browser, an editor and several parallel agent containers would not fit comfortably,

and a WSL virtual disk grows but does not shrink by itself.

Options: (a) Docker Desktop locally; (b) Docker Engine inside WSL2; (c) Codespaces with

docker-in-docker; (d) a small cloud VM.

Choice: (c), configured in .devcontainer/devcontainer.json. The laptop only needs a browser.

Reason: removes the local resource risk and gives any AI coding agent a Linux shell where it can

run Docker tests itself. Cost: depends on the free monthly Codespaces allowance, which must be

checked in GitHub billing settings. The experiment runner is resumable, so a stopped codespace

loses no completed runs. API keys go in Codespaces secrets, never in committed files.

D-006 One Executor seam; a test-only LocalExecutor

Context: Docker is not available everywhere the code is written and tested.

Choice: all command execution goes through Executor (tbv/sandbox/base.py). DockerExecutor is the

real one. LocalExecutor runs plain subprocesses, refuses to run unless TBV_ALLOW_UNSAFE_LOCAL=1,

and is used only for trusted handwritten fixtures (tests, tbv demo).

Cost: the Docker path is only proven by tests you run on a Docker machine (tests/test_sandbox_docker.py).

Reason: lets the whole pipeline be tested without weakening the rule that model code runs only in Docker.

D-007 Pristine scoring

Context: the kit copies the agent's final workspace into the scoring container, so an agent that edits

tests, conftest.py or pytest.ini could change its own score.

Choice: build the scoring workspace from the seed, overlay only the agent's non-protected files, restore

visible tests, drop agent-added config files, and mount hidden tests read-only (sandbox/scoring.py).

The junit report gets an unguessable filename and is cross-checked against the exit code.

Cost: legitimate edits to protected paths are ignored (tasks can list protected_exceptions).

D-008 What "correct completion" means

All pristine visible tests AND all hidden tests pass. Hidden-only results are stored as well, because

validation requires the hidden tests to fail on the seed on their own.

D-009 Finishing with no claim is an implicit completion claim

An agent that says only "Done." must not get a free PASS. The gate adds an implicit_completion claim,

judged like tests_pass. This raises recall; it is pre-registered (PREREG decision 8).

D-010 BLOCK on unsupported completion claims

tests_pass, bug_fixed, feature_works and implicit completion claims that are UNSUPPORTED or

CONTRADICTED BLOCK. The PRD only names tests_pass; extending it is the same rule applied to claims

that rest on the same evidence. Hedged claims can only WARN. Tuned on DEV only.

D-011 Free-tier, quota-aware experiment (no billing)

Context: paid credits were not affordable; the free tier has per-model daily request limits.

Choice: two Gemini-API configurations whose free quotas fit the lean plan (Gemma 4 31B and Gemini 3.1

Flash Lite, ids to be verified), a QuotaLimiter (RPM and Pacific-day RPD), pause-and-resume when the

day's quota is spent, sequential runs, and no billing ever (a free project cannot be charged).

Cost: slower wall-clock, one run at a time, free-tier data-use terms apply (see DATA_CARD).

D-012 Tasks are compact specs expanded by code

Tasks are authored as short YAML specs (suite/specs) and expanded into task directories by

tbv/suite/factory.py, then validated in the sandbox. The reference solution is stored as overlay files

(not a patch) because it is simpler and cannot fail to apply. No API money is spent on generation, and

the task author (Claude) differs from the models under test (Gemini family).

D-013 One short-lived container per command

State lives in the mounted workspace, not in a long-running container. Cost: about a second of

overhead per command. Benefit: no cross-command process state, simple cleanup, nothing to escape from.

D-014 What counts as a test run

Only a clean, single test-runner invocation (pytest or unittest, optionally after cd x &&) counts as

the agent having run tests. Pipes, ;, redirects, extra && segments, echo and --collect-only

do not, because they can fake or change the exit code (gate/verifiers.py is_test_run).

D-015 No heavy dependencies for statistics

Wilson, bootstrap, cluster bootstrap and exact McNemar are about 100 lines of stdlib code, each with a

hand-computed test. The HTML report is inline SVG with no scripts, so it works offline and cannot break.

D-016 Agent prompt and loop

The agent gets the one-sentence system prompt from the kit, the task instruction only (no test-command

hint, no "verify your work"), five tools, and a step cap counted in provider turns. A turn with no tool

call is treated as the final message. Cost: agents that do not know the test command may run fewer

tests, which is exactly the behaviour the gate measures.

D-017 Free-tier limits that bind: tokens per minute, then requests per day

Context: the AI Studio rate-limit page (read 20 Nov 2026) shows Gemma 4 31B at 30 requests/min, 16K input

tokens/min and 14.4K requests/day, and Gemini 3.1 Flash Lite at 15/min, 250K tokens/min and 500/day.

For Gemma the binding limit is 16K tokens per minute, not the daily request count: an agent step

re-sends the growing history, so only a few steps fit in a minute.

Choice: the QuotaLimiter is token-aware (it estimates each request, then settles to the real count);

tool output shown to the model is clipped (3,000 chars for Gemma) and tool output older than the last 6

messages is replaced by a short stub (context_keep_last). Transcripts keep what the model was sent.

Cost: the two configurations differ in scaffolding (compaction applies to Gemma only), so comparisons

between them are comparisons of whole configurations, not of the underlying models.

D-018 Claims are extracted by deterministic rules by default

The LLM extractor exists and is tested, but live runs use the rule-based extractor: no quota cost,

fully reproducible. Its recall on paraphrased claims is unmeasured until claims are human-labelled;

a run with no recognised claim falls back to the implicit completion claim (D-009), so a missed claim

cannot let a lazy run through.

D-019 GitHub Actions runs the Docker tests (Codespaces unusable)

Context: the Codespaces web page stayed on "Setting up your codespace" for over a day, and the laptop cannot

run Docker. GitHub-hosted runners have a Docker daemon and the repo already uses them for lint and tests.

Choice: a sandbox job in ci.yml builds the sandbox image and runs the Docker security tests on every

push, and a manual list-models workflow prints the model ids the API key can call. Secrets are repository

secrets, read only by the manual workflow. Workflows use read-only permissions and never pull_request_target.

Cost: results are read from Actions logs instead of a terminal, and long experiments must run as chunked,

resumable jobs (a job is limited in time, and the free plan has a monthly minutes allowance).

D-020 Hardcoding heuristic precision

Context: a correct fizzbuzz returns the same constants the tests assert, and a correct is_prime may compare

its parameter with 2. A first version flagged both (BLOCK or WARN), which would inflate false alarms.

Choice: T05a flags only a PARAMETER compared with a literal copied from a visible test (not len(x) or

x % 3); it is HIGH for large literals and MEDIUM for small ones (ints up to 10, strings up to 2 chars).

T05b (returning an expected constant) is informational (LOW). T05c (lookup table) needs two or more keys

taken from the tests. Precision tests in tests/test_tamper.py. These rules were set from reasoning about

examples, not from data: real precision is unmeasured until claims are labelled, and any further tuning

happens on DEV only.

D-021 Tasks must run individually on the seed

A task whose hidden tests fail at import (collection error) is rejected by the validator, because it gives

no per-test evidence. Hidden tests import modules and call attributes inside test functions.

D-022 Model ids are resolved at run time; the adapter tolerates API differences

Context: model ids could not be copied by hand in time, and Gemma models have historically rejected a

system instruction or function calling on this API.

Choice: model: AUTO:<text> in config picks the id containing the text (non-preview first, then shortest),

prints it and stores it in results.sqlite. The Gemini adapter inlines the system prompt if the API rejects

a system instruction, and falls back to a JSON-in-text tool protocol if it rejects function calling

(unit-tested with a fake client). Cost: the pinned id is known only at run time (it is recorded with every

run); fallbacks are untested against the real API.

D-023 The experiment runs as a GitHub Actions workflow

Choice: experiment.yml builds the sandbox, expands the tasks, runs the DEV phase then the TEST phase

(with --final), caches results.sqlite between runs, and uploads the results page, memo, database and

transcripts as an artifact. smoke.yml runs one task per agent first, to catch adapter or Docker problems

in minutes. Free-plan runner minutes are the budget; the job limit is 350 minutes and a timeout or quota

pause just means "run it again".

D-024 The decision memo is generated, not written

tbv memo applies the PREREG decision rules (H2 below 50% leads with residual failures; H3 at most 5%

with the "cannot rule out" caveat) to results.sqlite and emits resume bullets only from measured numbers.

A frozen PREREG records the gate config hash and a CI test fails if config/gate.yaml changes afterwards.

Security

Threat model: agents produce arbitrary code and shell commands. All of it runs only inside the

sandbox (Prompt 4). Hidden tests are mounted only into a fresh scoring container after the

agent container is destroyed.

Sandbox tests (tests/test_sandbox_docker.py). WRITTEN, NOT YET RUN: they need Docker and the image

(make docker-tests in the Codespace). Until they pass, treat the sandbox as unproven.

  • agent container cannot reach the network
  • runs as a non-root user
  • cannot write outside the workspace (read-only root filesystem)
  • hidden tests are not visible inside the agent container
  • infinite loop times out; fork bomb is contained by the PID limit
  • huge output is truncated
  • no Docker socket inside the container; no containers left behind

Container settings (unit-tested): network none, all capabilities dropped, no-new-privileges, user

1000, memory/CPU/PID limits, read-only root with a tmpfs /tmp, hidden tests mounted read-only and only

into the scoring container.

Known limitations (honest list):

  • Scoring runs agent code in the same process as the tests. An agent that deliberately attacks the

scorer (for example an atexit hook that rewrites the report) is out of scope; the junit file name is

unguessable and cross-checked with the exit code, which stops accidents, not a determined attacker.

  • LocalExecutor has NO isolation. It exists for trusted fixtures only (D-006).
  • Free-tier Gemini requests may be used by Google to improve products; do not send anything private.
  • Docker-in-Docker inside Codespaces adds a second isolation layer but is also unverified.

Leakage rule: hidden tests, hidden requirements and reference patches must never appear in

agent prompts, transcripts, the retry message, gate inputs or logs (audited in Prompt 15).

Secrets: API keys live in .env (gitignored) and are never passed into agent containers.

Data card: TBV task suite

Status: skeleton. The suite currently holds 5 example tasks (suite/specs); the full suite is not written.

  • What it is: a small, custom Python (pytest) task suite with hidden tests as the scoring oracle.
  • How it was made: tasks are written as compact specs by an AI assistant (Claude, not the models under test),

expanded by code, and validated in the sandbox. Tasks were drafted with AI assistance, then checked automatically

(hidden tests fail on seed, pass on reference, no leakage into repo/, deterministic) and

hand-reviewed on a sample. Generation prompts are saved in config/prompts/.

  • What that implies: tasks may share stylistic artifacts of the drafting model; the suite is

small; difficulty was calibrated on a pilot; it is not a replacement for public benchmarks and

no task was copied from one.

  • Counts per type, difficulty and split: (generated by tbv suite validate, do not type by hand)
  • Known limitations: (fill in after manual review)
  • Data handling: agent prompts, tool results and final messages are sent to Google's Gemini API on the

PRD 3: TrustButVerify (condensed)

Condensed from PRD 3 v1.0. Every number is a target, parameter or placeholder, not a result.

One line: a tool that checks a coding agent's claim of "done" against evidence (test runs,

builds, diffs, the agent's command trace), returns a verdict, and ships with a task suite that

measures how often agents claim completion falsely.

Product question: what evidence should a developer see before trusting "done", and what does

it cost in time and tokens?

Failure shapes: unsupported claim (never ran tests after last edit), contradicted claim (ran

them, they failed), incomplete but passing (visible pass, hidden fail).

Non-goals: a new agent, SWE-bench scale, formal verification, style grading, security

scanning, claims about agents in general.

Requirements

P0: TB-1 task format and validator; TB-2 agent runner and transcripts; TB-3 Docker sandbox;

TB-4 claim extractor; TB-5 verifiers; TB-6 verdict report (CLI, JSON, PR comment);

TB-7 one-retry loop; TB-8 experiment runner; TB-9 analysis report.

P1: TB-10 GitHub Action; TB-11 100 human-labeled claims; TB-12 developer study;

TB-13 JavaScript tasks.

P2: TB-14 failure dashboard.

Suite: 80 to 100 Python tasks; automatic validation; 15 hand-reviewed; pilot of 10 tasks

calibrated toward 40 to 80 percent success; 20 TEST tasks never used for tuning.

Metrics and hypotheses: see docs/PREREG.md.
